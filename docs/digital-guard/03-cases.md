## 사례 1 · C1-01 「과학 모둠 보고서 공유」

| 항목 | 내용 |
|---|---|
| 사건 ID | `C1-01` |
| 난이도 | 초급 (Day 1, 3번째 사례) — 단일 항목 비교 |
| 사건 설명 | 누리중 2학년 하은솔 학생이 구름서랍에 있는 '과학 모둠 보고서' 파일을 같은 모둠 친구 3명에게 공유하려고 한다. |
| 적용 규칙 | `R-SHARE-01` 파일은 과제 명단에 있는 사람에게만 공유한다. |
| 판정 선택지 | 승인 · 거부 |
| **정답 판정** | **승인** |

**검토 대상 문서**

```
📄 문서 1 — 구름서랍 공유 요청서
 요청자        하은솔 (eunsol.ha@baeumteo.example)
 파일 이름      과학_모둠보고서_3조.docx
 공유 대상      ① 박도윤  ② 이서아  ③ 최하준
 공유 방식      지정한 사람만
 권한          편집 가능

📋 문서 2 — 누리배움터 2-3반 과학 모둠 명단 (담당: 과학 선생님)
 3조           하은솔, 박도윤, 이서아, 최하준
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 공유 대상 ①②③ ↔ 명단 3조 | 3명 모두 일치 |
| 공유 방식 ↔ 규칙 | '지정한 사람만' — 문제없음 |

- **위험 요소 위치**: 없음 (정상 요청)
- **핵심 근거 필드(근거 확인 판정용)**: 문서1 `공유 대상` ↔ 문서2 `3조 명단`
- **판정 근거**: 공유 대상이 모두 같은 모둠원이고, 공유 방식도 지정한 사람으로 제한되어 있다.
- **교육용 해설**: "공유 대상 3명이 모두 3조 명단에 있어요. 같은 모둠 친구에게 '지정한 사람만' 방식으로 공유하는 건 안전한 공유예요. 보안 심사관은 위험을 막는 것만큼 **필요한 일을 할 수 있게 돕는 것**도 중요해요."
- **오답 시 힌트(거부를 선택한 경우)**: "요청서의 이름 3개를 명단과 하나씩 비교해 볼까요? 다른 이름이 있었나요?"
- **과잉 차단 후일담**: "은솔이네 모둠이 보고서를 함께 쓰지 못해 제출이 하루 늦어졌대요."

**화면 동작 예시**: 플레이어가 🔍 대조 → 요청서 `② 이서아` 탭 → 명단 탭으로 전환 → `3조` 필드 탭 → "✓ 일치: 이서아는 3조 명단에 있어요" 칩 생성. 3명 모두 확인 후 승인 → "정확한 판단이에요! 근거 확인 보너스 +20".

## 사례 2 · C1-02 「독서 동아리 신청 양식」

| 항목 | 내용 |
|---|---|
| 사건 ID | `C1-02` |
| 난이도 | 초급 (Day 2) — 단일 항목 비교 |
| 사건 설명 | 별빛 디지털 도서관 오서윤 사서가 '청소년 온라인 독서 동아리' 신청 양식을 공개하기 전에 센터에 검토를 맡겼다. 양식 초안은 동아리 학생 운영진이 만들었다. |
| 적용 규칙 | `R-PRIV-01` 목적에 꼭 필요한 정보만 수집한다. |
| 판정 선택지 | 승인 · 거부 |
| **정답 판정** | **거부** (수정 후 다시 요청하도록 안내) → 신고: **안내만 하기** |

**검토 대상 문서**

```
📝 문서 1 — 온라인 독서 동아리 신청 양식(초안)
 1. 닉네임
 2. 학년
 3. 좋아하는 책 장르
 4. 연락용 도서관 계정 ID
 5. 집 주소 (동·호수까지)          ← 
 6. 하고 싶은 말

📋 문서 2 — 오늘의 기준: 온라인 동아리 신청에 필요한 정보 (도서관 운영 지침)
 ✔ 닉네임  ✔ 학년(모둠 나누기용)  ✔ 연락용 도서관 계정
 ✔ 관심 분야  ✔ 자유 의견(선택)
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 양식 항목 1~6 ↔ 운영 지침 목록 | 5번 '집 주소'만 지침에 없음 |

- **위험 요소 위치**: 문서1 `항목 5. 집 주소`
- **판정 근거**: 온라인 동아리 활동에는 집 주소가 필요하지 않다. 목적과 관계없는 개인정보를 수집하는 양식이다.
- **교육용 해설**: "온라인 독서 동아리는 책 이야기를 나누는 모임이라 **집 주소가 필요 없어요.** 필요 없는 정보를 모으지 않는 걸 '개인정보 최소 수집'이라고 해요. 모은 정보가 적을수록 잃어버릴 위험도 적어요. 💬 이렇게 해요: 신청서를 쓸 때 '이 정보가 왜 필요할까?'를 먼저 생각해 봐요."
- **도서관 맥락 후일담(정답 시)**: 오서윤 사서 "도서관은 이용자의 개인정보를 지키는 곳이에요. 5번 항목을 빼고 다시 올릴게요!"
- **오답 시 힌트(승인을 선택한 경우)**: "양식의 항목을 운영 지침 목록과 하나씩 맞춰 보세요. 목록에 없는 항목이 있나요?"
- **보조 학습**: 🚩 표시 도구가 처음 열리는 날이므로, 정답 후 "5번 항목에 깃발을 꽂으면 위험 탐지 점수를 받을 수 있어요"라는 안내 1회.

## 사례 3 · C1-03 「새 비밀번호 점검」

| 항목 | 내용 |
|---|---|
| 사건 ID | `C1-03` |
| 난이도 | 초급 (Day 3) — 단일 항목 비교, 함정 1개(길이 조건은 통과) |
| 사건 설명 | 정은우 학생이 누리배움터 비밀번호를 바꾸려 한다. 센터의 '비밀번호 점검기'가 새 비밀번호의 구성을 분석해 보여 준다. (게임 속 가상 비밀번호이며, 플레이어가 직접 비밀번호를 입력하는 기능은 없다.) |
| 적용 규칙 | `R-PW-01` 비밀번호는 10자 이상이며, 이름·생일·학번·전화번호 같은 개인정보를 넣지 않는다. |
| 판정 선택지 | 승인 · 거부 |
| **정답 판정** | **거부** (다른 비밀번호를 만들도록 안내) → 신고: **안내만 하기** |

**검토 대상 문서**

```
👤 문서 1 — 누리배움터 계정 프로필
 이름          정은우 (영문: Jeong Eunwoo)
 생일          3월 12일
 학번          20517

🔐 문서 2 — 비밀번호 점검표
 새 비밀번호     eunwoo0312!
 길이          11자            ✔ 10자 이상
 포함된 조각     'eunwoo' / '0312' / '!'
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 길이 11자 ↔ 10자 이상 | 통과 (함정: 이것만 보고 승인하기 쉬움) |
| 조각 'eunwoo' ↔ 프로필 영문 이름 | **영문 이름이 그대로 포함됨** |
| 조각 '0312' ↔ 프로필 생일 3월 12일 | **생일이 포함됨** |

- **위험 요소 위치**: 문서2 `포함된 조각: eunwoo`, `포함된 조각: 0312`
- **판정 근거**: 길이 조건은 맞지만 이름과 생일이 그대로 들어 있어 다른 사람이 쉽게 추측할 수 있다.
- **교육용 해설**: "길이는 충분하지만 **이름(eunwoo)과 생일(0312)**이 들어 있어요. 이름과 생일은 친구나 SNS로 쉽게 알 수 있는 정보라 추측당하기 쉬워요. 💬 이렇게 해요: 나만 아는 *긴 문장*을 떠올려 비밀번호로 만들고, 서비스마다 다르게 써요. (예: 좋아하는 장면을 짧은 문장으로 바꾸기)"
  - ※ 해설에서는 '좋은 비밀번호의 원리'만 설명하고, 실제로 쓸 수 있는 완성형 비밀번호 예시는 제시하지 않는다(예시를 그대로 따라 쓰는 것을 방지).
- **오답 시 힌트(승인을 선택한 경우)**: "길이는 통과했어요. 그런데 비밀번호 조각 중에 프로필에서 본 정보가 있지 않나요?"

- **교육용 해설**: "이 메일은 **진짜 누리배움터 주소가 아닌 곳**에서 왔어요. 인터넷 주소는 끝부분이 '진짜 주인'이에요. `baeumteo.login-check.example`의 주인은 `login-check.example`이에요. 이렇게 믿을 만한 곳인 척 속이는 메시지를 **피싱**이라고 해요. 💬 이렇게 해요: 메일 속 링크 대신 *앱이나 즐겨찾기로 직접* 들어가 공지를 확인하고, 의심 메일은 신고해요."


| 관련 정보와 비교 기준 | 결과 |

| 파일 내용(보호자 연락처·집 주소) ↔ 요청 목적('역할 분담 확인') | **목적에 불필요한 개인정보 포함** |
| 권한 '보기만 가능' | 문제 아님 (함정: 권한만 보고 안전하다고 판단하기 쉬움) |

  - ✅ 공개 범위가 '링크가 있는 모든 사람'이다
  - ✅ 역할 확인에 필요 없는 보호자 연락처와 집 주소가 들어 있다

- **오답 시 힌트(승인)**: "권한은 '보기만 가능'이 맞아요. 그런데 *누가* 볼 수 있는지, 그리고 파일 안에 *무엇이* 들어 있는지도 살펴볼까요?"
- **허용 대안**: '추가 확인' 선택 시 → 부분 점수 + "확인해 볼 수도 있지만, 이 사례는 이미 위험 요소가 분명해서 거부하고 안전한 방법을 안내하는 것이 더 좋아요."

## 사례 9 · C4-01 「동아리 게시판 관리자 권한」

| 항목 | 내용 |
|---|---|
| 사건 ID | `C4-01` |
| 난이도 | 심화 (Day 15) — 권한 변경 + 불완전한 정보, *진짜일 수도 있는 요청* |
| 사건 설명 | 별빛 디지털 도서관 독서 동아리 부원 서지우 학생이 "다음 주부터 제가 부장이 돼요. 오서윤 사서 선생님이 관리자 권한을 받으라고 하셨어요."라며 동아리 게시판 관리자 권한을 요청했다. |
| 적용 규칙 | `R-PERM-01` 관리자 권한은 담당자의 승인 기록이 있어야 준다. / `R-PERM-02` 역할에 필요한 만큼만 권한을 준다. / `R-VERIFY-01` 정보가 부족하면 공식 경로로 확인한다. |
| 판정 선택지 | 승인 · 거부 · 추가 확인 |
| **정답 판정** | **추가 확인** — 확인 경로: "도서관 공식 업무 연락처로 오서윤 사서에게 확인" |
| 허용 대안 | 거부 (부분 점수 50%, '안전하지만 과잉 차단 가능성' 해설) |

**검토 대상 문서**

```
📄 문서 1 — 권한 요청서
 요청자        서지우 (jiwoo.seo@byeolbit-lib.example)
 요청 권한      게시판 관리자 (글 삭제, 회원 목록·이메일 열람 포함)
 사유          다음 주부터 부장 역할
 승인자         (비어 있음)

📋 문서 2 — 독서 동아리 운영진 명단 (현재)
 부장  김나래    부원  서지우 외 11명

📢 문서 3 — 동아리 공지 (10/10, 작성: 김나래)
 "다음 주에 운영진이 바뀔 예정이에요. 새 부장은 투표로 정해요."

📇 문서 4 — [공식 연락처 조회] 별빛 디지털 도서관 업무 연락처
 독서 동아리 담당: 오서윤 사서 (업무 메일 seoyun.oh@byeolbit-lib.example)
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 요청자 역할 ↔ 현재 운영진 명단 | 현재는 일반 부원 (권한 근거 없음) |
| 사유 '다음 주 부장' ↔ 동아리 공지 | 운영진 교체 예정은 **사실**. 그러나 새 부장이 서지우인지는 **확인되지 않음** |
| 승인자 칸 ↔ R-PERM-01 | **비어 있음** — 승인 기록 없음 |
| 요청 권한 범위 ↔ R-PERM-02 | 회원 이메일 열람까지 포함 — 부장 역할에 꼭 필요한지 담당자 판단 필요 |

- **위험 요소 위치(확인이 필요한 지점)**: 문서1 `승인자(비어 있음)`(필수), 문서1 `요청 권한 범위`(선택)
- **판정 근거**: 요청이 사실일 가능성(운영진 교체 공지)은 있지만 담당자의 승인 기록이 없다. 바로 승인하면 위험하고, 바로 거부하면 정당한 요청을 막을 수 있으므로 공식 경로로 확인한다.
- **확인 경로 선택 보기**
  - ✅ 도서관 공식 업무 메일로 오서윤 사서에게 확인한다
  - ❌ 서지우 학생에게 "정말이에요?"라고 다시 물어본다 *(요청자 본인의 말은 확인이 되지 않음)*
  - ❌ 동아리 단체 대화방에 물어본다 *(공식 경로 아님, 정보 노출)*
- **교육용 해설**: "운영진이 바뀐다는 공지는 진짜예요. 하지만 **누가** 새 부장인지, 사서 선생님이 **정말 허락했는지**는 아직 몰라요. 이럴 땐 무조건 막거나 열어 주지 말고, **공식 연락처로 담당자에게 확인**하는 게 가장 좋아요. 관리자 권한에는 다른 회원의 이메일을 보는 기능도 있어서, 꼭 필요한 사람에게만 줘야 해요."
- **오답 시 힌트(승인)**: "승인자 칸을 확인해 봤나요? 관리자 권한을 주려면 무엇이 필요했죠?"
- **오답 시 힌트(거부 → 허용 대안 해설)**: "안전한 선택이에요. 그런데 공지를 보면 이 요청은 진짜일 수도 있어요. 막기 전에 확인할 방법은 없을까요?"
- **후일담(정답)**: 오서윤 사서 "확인해 줘서 고마워요. 투표는 내일이라 아직 부장이 정해지지 않았어요. 정해지면 제가 직접 승인할게요!"

## 사례 10 · C4-02 「"선생님"의 긴급 부탁」 (2단계 사례)

| 항목 | 내용 |
|---|---|
| 사건 ID | `C4-02` (단계: `C4-02-S1` → `C4-02-S2`) |
| 난이도 | 심화 (Day 16) — 긴급 요청 + 권한 변경 + 사칭 + 불완전 정보 + 인증 코드 |
| 사건 설명 | 하은솔 학생(학급 출석 도우미, 출석부 파일 관리자)이 말풍선 메신저로 "담임 선생님"이라는 사람에게 메시지를 받고 센터에 문의했다. |
| 적용 규칙 | 1단계: `R-ID-01`, `R-VERIFY-01` / 2단계: `R-ID-01`, `R-PW-02` 비밀번호·인증 코드는 누구에게도 알려 주지 않는다, `R-REPORT-01` |

### 1단계 (C4-02-S1) — 정보가 불완전한 긴급 요청

**검토 대상 문서**

```
💬 문서 1 — 말풍선 메시지
 보낸 사람      "2-3반 담임 김서연" (등록되지 않은 번호, 프로필 사진: 학교 로고)
 내용          "은솔아, 선생님 휴대폰을 바꿔서 이 번호로 연락해.
               지금 회의 중이라 급해! 학급 출석부 파일 편집 권한을
               아래 계정에 바로 줘. 10분 안에 해야 해."
 요청 계정      kim.teacher.class3@freemail.example

📄 문서 2 — 구름서랍 권한 변경 요청 (자동 생성)
 파일          2-3반_출석부.xlsx
 추가할 사람     kim.teacher.class3@freemail.example
 권한          편집 가능

📇 문서 3 — [공식 연락처 조회] 누리중학교 교직원 공식 연락처
 2-3반 담임    김서연 선생님  공식 계정 kim.sy@baeumteo.example
                           학교 교무실 000-0000-2300
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 요청 계정 `@freemail.example` ↔ 공식 계정 `kim.sy@baeumteo.example` | **불일치** — 공식 계정이 아님 |
| 보낸 번호 '등록되지 않은 번호' ↔ 공식 연락처 | 확인할 수 없음 |
| "휴대폰을 바꿨다"는 설명 | 사실일 수도 있음 → 신원이 *거짓으로 밝혀진 것*은 아니고 *확인되지 않은* 상태 |
| '10분 안에', '급해' | 서두르게 하는 표현 (판단을 서두르지 말라는 신호) |

- **판정 선택지**: 승인 · 거부 · 추가 확인
- **정답 판정**: **추가 확인** — 확인 경로 "학교 공식 연락처(교무실)로 김서연 선생님께 확인"
- **판정기 관점**: `R-ID-01`의 신원 상태가 *미확인(Unconfirmed)* → 결과 '알 수 없음' → `R-VERIFY-01`에 따라 추가 확인. 거부 수준 위반은 아직 없음.
- **허용 대안**: 거부 (부분 점수 70%). 해설: "공식 계정이 아니니 막은 건 잘했어요! 그런데 진짜 선생님이 정말 곤란한 상황일 수도 있으니, 공식 연락처로 확인하면 은솔이도 선생님도 안심할 수 있어요." (허용 대안을 고르면 2단계 대신 해설 후 다음 사례로)
- **오답(승인) 힌트**: "요청 계정을 교직원 공식 연락처와 비교해 봤나요? 공식 계정이 아닌데 바로 편집 권한을 줘도 될까요?"
- **확인 경로 선택 보기**
  - ✅ 학교 교무실 공식 번호로 전화해 확인한다
  - ❌ 메시지를 보낸 번호로 "진짜 선생님 맞아요?"라고 답장한다 *(상대가 사칭자라면 "맞다"고 답할 것)*
  - ❌ 일단 권한을 주고 나중에 확인한다
- **위험 요소 위치(1단계)**: 문서1 `요청 계정`(필수), 문서1 `보낸 사람(등록되지 않은 번호)`(선택), 문서1 `10분 안에`(선택)

### 2단계 (C4-02-S2) — 추가 확인 결과 도착

```
📞 문서 4 — 확인 결과 (센터 → 누리중 교무실)
 "김서연 선생님은 오늘 휴대폰을 바꾸지 않았고, 그런 메시지를
  보낸 적이 없다고 하십니다. 출석부 권한은 학교 계정으로만 관리합니다."

💬 문서 1-2 — 같은 번호에서 온 새 메시지 (확인하는 사이 도착)
 "왜 아직 안 해? 그럼 방금 네 폰으로 간 인증번호 6자리라도 보내 줘."
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 확인 결과 ↔ 메시지 발신자의 주장 | 선생님이 보낸 메시지가 아님 → 신원 *거짓 확인(Refuted)* |
| '인증번호 6자리 보내 줘' ↔ `R-PW-02` | **위반** — 인증 코드는 누구에게도 알려 주면 안 됨 |

- **판정 선택지**: 승인 · 거부 *(추가 확인은 이미 사용했으므로 표시하지 않음)*
- **정답 판정**: **거부** → 신고: **신고하기**
- **위험 요소 위치(2단계)**: 문서4 `확인 결과`(필수), 문서1-2 `인증번호 요구`(필수)
- **판정 근거**: 공식 연락처로 확인한 결과 선생님이 보낸 메시지가 아니다. 다른 사람이 선생님을 사칭해 파일 권한과 인증 코드를 얻으려 했다.
- **교육용 해설**: "급하다고 하면 마음이 바빠지죠. 그럴수록 **공식 연락처로 확인**하는 게 중요해요. 메시지에 적힌 번호로 다시 물어보면 같은 사람이 답할 수 있어서 확인이 되지 않아요. 그리고 **인증번호는 선생님, 친구, 운영자 누구에게도 알려 주지 않아요.** 인증번호는 '지금 로그인하는 사람이 나'라는 걸 증명하는 열쇠라서, 남에게 주면 내 계정 문을 열어 주는 것과 같아요. 💬 이렇게 해요: 이상한 메시지는 캡처해 두고 보호자나 선생님께 알린 뒤 신고해요."
- **오답(승인) 힌트**: "확인 결과를 다시 읽어 볼까요? 그리고 인증번호는 누구에게 알려 줘도 될까요?" (2차 오답 시에도 은솔이가 *인증번호를 보내기 전에* 센터가 막았다는 후일담으로 처리하고 피해 장면은 묘사하지 않음)
- **후일담(정답)**: 김서연 선생님(공식 계정) "은솔아, 확인해 줘서 정말 고마워. 반 친구들에게도 조심하라고 알려 줄게."

**화면 동작 예시**: 1단계에서 '추가 확인' → 확인 경로 시트에서 "교무실 공식 번호" 선택 → 0.8초 '연락 중…' 연출(움직임 줄이기 시 생략) → 문서 트레이에 문서4·문서1-2가 ● 표시와 함께 추가 → 판정 패널이 [승인][거부] 2개로 바뀜 → 거부 → 신고 도장 연출 → 해설.

### 사례 11 · C2-04 「택배 주소 확인 문자」

| 항목 | 내용 |
|---|---|
| 사건 ID | `C2-04` |
| 난이도 | 중급 (Day 5) — 문자·공식 목록·내 기록 세 자료 대조 |
| 사건 설명 | 박영순 님(은솔이의 할머니)이 "택배 주소가 잘못돼서 보관 중이래요. 링크 눌러서 주소를 다시 써야 하나요?"라고 문의했다. 승인 = 링크 접속 허용, 거부 = 접속 차단. |
| 적용 규칙 | `R-LINK-01` 링크와 보낸 곳은 공식 목록과 일치해야 한다. / `R-REPORT-01` |
| 판정 선택지 | 승인 · 거부 |
| **정답 판정** | **거부** → 신고: **신고하기** |

**검토 대상 문서**

```
💬 문서 1 — 받은 문자
 보낸 번호      000-0000-9911
 내용          [콩콩택배] 주소지 불명으로 상품이 보관 중입니다.
              아래에서 주소를 다시 입력해 주세요.
 링크          http://kongkong-delivery.example/a1

📋 문서 2 — 공식 연락처 목록 (센터 자료)
 콩콩택배       공식 주소: kongkong.example
              대표 번호: 000-0000-1500

👤 내 기록 — 박영순
 최근 7일 주문   없음
 기다리는 택배   없음
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 링크 도메인(끝부분) `kongkong-delivery.example` ↔ 공식 `kongkong.example` | **불일치** — 이름만 비슷한 다른 주소 |
| 보낸 번호 ↔ 대표 번호 | 다름 (보조 단서) |
| 택배 알림 ↔ 내 기록 '최근 주문 없음' | 기다리는 택배가 없다 |

- **위험 요소 위치**: 문서1 `링크`(필수), 문서1 `보낸 번호`(선택)
- **핵심 근거**: 문서1 `링크` ↔ 문서2 `공식 주소`, 문서1 `내용` ↔ 내 기록 `최근 7일 주문`
- **판정 근거**: 공식 주소가 아닌 링크로 주소 입력을 유도하고, 받을 택배도 없다.
- **교육용 해설**: "주소의 끝부분을 보면 이 링크의 주인은 `kongkong-delivery.example`이에요. 콩콩택배의 공식 주소는 `kongkong.example`이고요. 게다가 할머니는 요즘 주문한 물건이 없었어요. 💬 이렇게 해요: 택배 문자는 링크를 누르지 말고, 평소 쓰던 쇼핑 앱이나 택배 회사 대표 번호로 확인해요."
- **오답 시 힌트(승인)**: "할머니의 기록을 볼까요? 기다리던 택배가 있었나요? 그리고 링크 주소를 끝에서부터 읽어 보세요."
- **짝 사례(같은 Day)**: 대표 번호에서 온 배송 알림, 링크 `kongkong.example/track`, 내 기록에 바구니마켓 주문 1건 → 정답 **승인**.

| 적용 규칙 | `R-FILE-03` 압축 파일은 내용 목록을 확인하고, 실행 파일이 들어 있으면 열지 않는다. / `R-ID-01` |

**검토 대상 문서**

```
💬 문서 1 — 받은 메시지 (말풍선)
 보낸 사람      아들 (저장된 연락처)
 내용          어머니, 추석 때 찍은 사진 모아서 보내요.
 📎 첨부        추석사진_모음.zip (48MB)

📎 문서 2 — 파일 정보 보기
 파일 이름      추석사진_모음.zip
 종류          압축 파일 (.zip)
 내용 목록      IMG_0901.jpg ~ IMG_0924.jpg (사진 24개)
              송편빚기.mp4 (동영상 1개)

👤 내 기록 — 박영순
 저장된 연락처   아들  000-0000-4410
 최근 대화      (어제) 아들: "내일 사진 정리해서 보내 드릴게요"
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 보낸 사람 ↔ 저장된 연락처 | 저장된 번호에서 왔다 |
| 메시지 내용 ↔ 최근 대화 | 어제 보내 주겠다고 한 사진이다 |
| 압축 내용 목록 ↔ `R-FILE-03` | 사진(.jpg)과 동영상(.mp4)뿐, 실행 파일 없음 |

- **위험 요소 위치**: 없음 (정상 요청)
- **핵심 근거**: 문서2 `내용 목록`, 문서1 `보낸 사람` ↔ 내 기록 `저장된 연락처`
- **판정 근거**: 아는 사람이 미리 말한 사진을 보냈고, 압축 안에도 사진과 동영상만 있다.
- **교육용 해설**: "압축 파일이라고 다 위험한 건 아니에요. **안에 무엇이 들어 있는지** 보는 게 중요해요. 이 파일에는 사진 24장과 동영상 1개만 있고, 어제 아드님이 보내 주겠다고 한 그 사진이에요. 💬 이렇게 해요: 압축 파일을 받으면 내용 목록부터 보고, `.exe`나 `.apk`처럼 *설치하거나 실행하는 파일*이 섞여 있으면 열지 않아요." (현실에서는 파일 이름만으로 안전을 장담할 수 없으므로, 모르는 사람이 보낸 파일은 더 조심한다는 문장을 해설 끝에 덧붙인다.)
- **오답 시 힌트(거부)**: "파일 정보에서 압축 안에 든 파일들의 끝 글자를 확인해 볼까요? 할머니의 최근 대화도 함께 보세요."
- **과잉 차단 후일담**: "할머니가 손주들 사진을 보지 못해 아쉬워하셨대요."

**검토 대상 문서**

```
✉ 문서 1 — 받은 메일
 보낸 사람      바구니마켓 입점지원 <partner@bagooni.example>
 내용          요청하신 견적서 PDF 파일을 보내 드립니다.
 📎 첨부        견적서_최종.pdf        .exe  (2.1MB)

📎 문서 2 — 파일 정보 보기
 전체 파일 이름  견적서_최종.pdf        .exe
 마지막 확장자   .exe
 종류          실행 파일 (프로그램)

👤 내 기록 — 이하늘
 보낸 요청      (10/14) 바구니마켓에 견적서 요청
 받을 파일      견적서 (PDF)
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 보낸 주소 ↔ 공식 도메인 `bagooni.example` | 일치 (함정: 주소만 보고 승인하기 쉬움) |
| 메일의 "PDF 파일" ↔ 실제 마지막 확장자 `.exe` | **불일치** — 문서처럼 보이게 이름 중간에 `.pdf`를 넣고 공백 뒤에 `.exe`를 숨겼다 |
| 받을 파일(PDF) ↔ 실행 파일 | 요청한 종류가 아니다 |

- **위험 요소 위치**: 문서2 `마지막 확장자`(필수), 문서1 `첨부`(필수)
- **판정 근거**: 보낸 주소는 공식이지만, PDF라고 한 파일이 실제로는 실행 파일이다. 계정이 도용됐을 가능성도 있다.
- **교육용 해설**: "파일의 진짜 종류는 **이름의 맨 끝**이 정해요. `견적서_최종.pdf        .exe`는 중간의 `.pdf`가 아니라 마지막 `.exe` 때문에 *실행 파일*이에요. 보낸 주소가 맞더라도 요청한 것과 종류가 다르면 열지 않아요. 💬 이렇게 해요: 파일을 열지 말고, 보낸 곳의 *원래 알던 전화번호*로 '이 파일 보내신 것 맞나요?' 하고 확인한 뒤 신고해요."
- **오답 시 힌트(승인)**: "파일 정보에서 이름의 *맨 끝* 글자를 확인해 보세요. 하늘 님이 받기로 한 파일은 어떤 종류였나요?"
- **짝 사례(같은 Day, 위험하지 않은 차이)**: 같은 거래처가 "견적서 보내 드려요"라며 `견적서.hwp`(한글 문서)를 보냄. 하늘 님은 PDF를 기대했지만 `.hwp`도 *문서 파일*이므로 정답 **승인**. 해설: "기대한 형식과 달라도 *문서끼리의 차이*는 위험 신호가 아니에요. 실행 파일인지가 중요해요."

### 사례 14 · C3-03 「손녀라는 새 번호」

| 항목 | 내용 |

**검토 대상 문서**

```
💬 문서 1 — 받은 메시지 (말풍선)
 보낸 번호      000-0000-7720 (저장되지 않은 번호)
 내용          할머니 나 은솔이야. 폰 액정이 깨져서 친구 폰 빌렸어.
              이따가 부탁할 게 있어. 이 번호로 답장해 줘.

👤 내 기록 — 박영순
 저장된 연락처   은솔(손녀)  000-0000-3301
 최근 대화      (그제) 은솔: "할머니 주말에 갈게요!" — 저장된 번호
```

| 관련 정보와 비교 기준 | 결과 |
|---|---|
| 보낸 번호 ↔ 저장된 은솔이 번호 | 다름 |
| "폰이 깨졌다"는 설명 | 사실일 수도 있음 → 신원이 *거짓으로 밝혀진 것*은 아니고 *확인되지 않은* 상태 |
| 아직 돈·인증번호 요구는 없음 | 거부해야 할 위반은 아직 없다 |

- **위험 요소 위치(확인이 필요한 지점)**: 문서1 `보낸 번호`(필수), 문서1 `이 번호로 답장해 줘`(선택)
- **근거 선택 보기** (추가 확인 근거)
  - ✅ 저장된 번호가 아닌 번호에서 왔다
  - ✅ 가족이라는 말만 있고 확인할 방법이 메시지 안에 없다
  - ❌ 메시지가 짧다 *(판정과 무관)*
  - ❌ 은솔이는 원래 문자를 안 보낸다 *(기록에 없는 추측)*
- **확인 경로 선택 보기**
  - ✅ 저장된 은솔이 번호로 직접 전화한다
  - ❌ 이 번호로 "진짜 은솔이 맞니?"라고 답장한다 *(상대가 사칭자라면 "맞다"고 답할 것)*
  - ❌ 부탁을 먼저 들어 보고 판단한다
- **확인 결과 카드** (추가 확인 정답 시, [G4](01-overview.md#33-게임플레이-단계-점검-v02)): "저장된 번호로 전화하자 은솔이가 받았어요. '할머니, 제 폰 멀쩡해요! 그거 저 아니에요.'"
- **교육용 해설**: "가족이라고 해도 **처음 보는 번호**라면 먼저 확인해요. 메시지에 적힌 번호로 묻지 말고, *원래 저장해 둔 번호*로 직접 전화하면 바로 알 수 있어요. 💬 이렇게 해요: 확인된 사칭 번호는 차단하고 신고해요. 가족끼리 '확인 질문'을 미리 정해 두는 것도 좋아요."
- **오답 시 힌트(승인)**: "할머니의 저장된 연락처와 보낸 번호가 같나요?"
- **허용 대안 해설(거부)**: "막은 건 좋아요. 그런데 진짜 은솔이가 곤란한 상황일 수도 있으니, 저장된 번호로 확인하면 확실해요."
- **후일담(정답)**: 박영순 님 "은솔이 목소리를 듣고 나니 마음이 놓여요. 주말에 같이 이 게임 해 보기로 했어요."

## 5.12 사례 작성 체크리스트 (콘텐츠 제작용)

새 사례를 만들 때 아래를 모두 만족해야 레벨 데이터에 넣을 수 있다. (에디터 검증 도구가 자동 확인하는 항목은 ⚙ 표시)

- [ ] ⚙ 정답 판정이 규칙 판정기의 계산 결과와 같다
- [ ] ⚙ 위험 요소 위치(`riskSpots`)가 모두 실제 문서 필드를 가리킨다
- [ ] ⚙ 정답 판정이 해당 사례의 판정 선택지 안에 있다
- [ ] ⚙ 근거 선택 보기 중 정답 근거가 1개 이상, 오답 근거가 1개 이상 있다(고급 이상)
- [ ] ⚙ 모든 문자열이 현지화 테이블에 등록되어 있다
- [ ] ⚙ 이메일·URL 도메인이 `.example`로 끝난다
- [ ] ⚙ 문서 안에 정답을 암시하는 문장("답장할 필요 없어요", "안전한 메시지예요" 등)이 없다
- [ ] ⚙ 첨부 파일의 마지막 확장자·파일 종류·압축 내용 목록이 서로 맞는다 ([부록 E](10-appendix.md#e-확장자-도감-파일-종류))
- [ ] ⚙ 거부가 정답이면 신고 정답(`reportable`)이 지정되어 있다
- [ ] 내 기록 탭에는 요청자가 *원래 알던 정보*만 있고, 메시지가 주장하는 내용은 들어가지 않는다
- [ ] 특정 세대를 깎아내리는 표현이 없다
- [ ] 실존 인물·기관·서비스명·상표를 쓰지 않았다
- [ ] 공격 방법을 알려 주는 내용이 없다
- [ ] 해설이 공포가 아니라 *실천 팁(💬 이렇게 해요)*으로 끝난다
- [ ] 오답 힌트가 정답을 직접 말하지 않고 *어디를 볼지*를 알려 준다
- [ ] 초등 고학년이 읽을 수 있는 어휘이며, 새 용어는 용어 사전에 있다
